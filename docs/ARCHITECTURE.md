# Architecture

This document describes the system as it currently exists and has been
verified to run. It does not describe planned functionality; see
`ROADMAP.md` for that.

> **No generative LLM, GraphRAG, or Neo4j integration currently exists in
> this project.** All responses are produced by direct database queries,
> deterministic routing logic, or verbatim retrieval of stored text — no
> text is generated by a language model at any point.

## Components

### FastAPI backend (`app/api`)

Exposes the HTTP API consumed by the Streamlit UI:

- `GET /health`
- `GET /shipments/{shipment_id}`
- `GET /shipments/{shipment_id}/events`
- `GET /analytics/delay-rates`
- `GET /analytics/high-risk-shipments`
- `POST /assistant/sop-search`
- `POST /assistant/chat`

Routing is split into `app/api/routes/shipments.py`,
`app/api/routes/analytics.py`, and `app/api/routes/assistant.py`, each
delegating to a service module.

### Streamlit interface (`app/ui/streamlit_app.py`)

A multi-page UI (Home, Shipment Lookup, Shipment Events, Delay Analytics,
High-Risk Shipments, SOP Assistant, Assistant Chat) that calls the FastAPI
backend over HTTP (`requests`) at a fixed base URL
(`http://127.0.0.1:8000`). It performs no data access or business logic of
its own — all data comes from the API.

### DuckDB operational database (`app/db`, `data/processed/logistics.duckdb`)

`app/db/connection.py` opens read-only DuckDB connections and exposes
`fetch_one` / `fetch_all` helpers used by the service layer. The database is
a local file built from the synthetic CSVs; it is not committed to version
control and is rebuilt via the loader script.

### Synthetic data generator and loader (`app/data`)

- `generate_synthetic_data.py` produces carriers, customers, routes,
  shipments, shipment events, and exceptions as CSV files under
  `data/processed/`, using NumPy/Pandas with a fixed random seed for
  reproducibility.
- `load_data.py` loads those CSVs into the DuckDB database and runs basic
  row-count and referential-consistency validation (e.g., every
  exception-flagged shipment has a matching exception record).

### Chroma vector store and Sentence Transformer embeddings (`app/rag`)

- `ingest_docs.py` reads the markdown SOP documents in
  `data/sample_sops/`, splits them into section/paragraph-sized chunks, and
  embeds each chunk with the `sentence-transformers/all-MiniLM-L6-v2` model.
  Embeddings and chunk text are stored in a local, persistent Chroma
  collection under `data/processed/chroma/`.
- `retriever.py` embeds an incoming question with the same model, queries
  the Chroma collection for the top matching chunks, and returns them with
  their source document and distance score. It also builds a simple
  extractive answer by concatenating the retrieved chunk text — no text is
  generated.

### Deterministic assistant routing (`app/services/assistant_service.py`)

Given a natural-language question, `route_question` uses a shipment-ID regex
and keyword matching to classify the question into one of: shipment lookup,
shipment events, delay analytics, high-risk shipments, or SOP search.
`build_chat_response` then calls the corresponding service function and
returns its result along with the chosen route. There is no model in this
path — routing is rule-based and fully deterministic for a given input.

### Shipment lookup and analytics services (`app/services/shipment_service.py`)

Contains the SQL queries and thin wrapper functions used by both the API
routes and the assistant:

- `get_shipment_details` / `get_shipment_events` — single-shipment lookups.
- `get_delay_rates` — delay rate and average delay days grouped by carrier
  and lane.
- `get_high_risk_shipments` — shipments that are delayed, exception-flagged,
  or on a route with a historically elevated delay rate.

### SOP retrieval flow

1. A question arrives via `/assistant/sop-search` or is routed to SOP search
   by `/assistant/chat`.
2. `retrieve_sop_chunks` embeds the question and queries Chroma for the
   top-k matching chunks (default 3).
3. `extractive_answer_from_chunks` concatenates the retrieved chunk text and
   collects the distinct source document names.
4. The response includes the concatenated answer text, the list of source
   documents, and the raw chunks (text, source, chunk index, distance).

## Current Data Flow

```
generate_synthetic_data.py --> CSV files (data/processed/*.csv)
                                       |
                                       v
                              load_data.py --> logistics.duckdb
                                       |
                                       v
                         FastAPI (app/api) <-- app/services (SQL queries)
                                       |
                                       v
                         Streamlit UI (app/ui) [HTTP calls]

data/sample_sops/*.md --> ingest_docs.py --> Chroma collection
                                                  |
                                                  v
                                       retriever.py <-- FastAPI /assistant routes
```

## Repository Structure

```
app/
├── api/
│   ├── main.py                 FastAPI app and /health endpoint
│   └── routes/                 shipments, analytics, assistant routers
├── core/
│   └── config.py                project paths and service name constant
├── data/
│   ├── generate_synthetic_data.py
│   └── load_data.py
├── db/
│   └── connection.py            DuckDB read-only connection helpers
├── rag/
│   ├── ingest_docs.py           SOP chunking, embedding, Chroma ingestion
│   └── retriever.py             embedding-based retrieval + extractive answer
├── services/
│   ├── assistant_service.py     deterministic question routing
│   └── shipment_service.py      shipment/analytics SQL queries
└── ui/
    └── streamlit_app.py          Streamlit front end

data/
├── processed/                   generated CSVs, DuckDB file, Chroma store (not committed)
├── raw/                         reserved for future raw source data (currently empty)
└── sample_sops/                 sample SOP/FAQ markdown documents

docs/                             project documentation (this set of files)
requirements.txt                  pinned Python dependencies
docker-compose.yml                currently empty; no Docker setup exists yet
```
